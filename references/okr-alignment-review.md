# OKR 对齐评审

## 对齐的定义

对齐是对目标内容、优先级、承接关系、协作方式和责任边界达成共同理解。存在上下级关系不等于自动对齐；存在业务相关性也不等于已经完成对齐。

同时检查两条链：

- 纵向：团队负责人 O → 个人 O/KR，确认承接的重点、范围和结果标准。
- 横向：跨团队或同级 O 之间的依赖、接口、冲突和主责，确认谁负责结果、谁提供协作。

在两条链之外，先做关系回溯：上周期本人完成情况、本周期本人被 @、上周期本人 @ 他人、直属上级当前周期 OKR。关系回溯用于发现承接和依赖，不能替代双方确认。

## 三阶段工作流

### 会前

1. 确认周期、参会范围、会议顺序和目标负责人。
2. 让参与者完成 OKR 初稿，并 @ 主要协作方。
3. 阅读团队成员的 O/KR，添加评论和对齐建议。
4. 从四个维度预审：写法规范、团队业务重点、KR 对 O 的支撑、协作关系。
5. 对涉及敏感数据、主责冲突或跨部门依赖的事项提前私聊。
6. 对照上周期完成度和 @ 关系，标出未闭环协作、重复依赖和本周期需要重新确认的对象。

### 会中

1. 先由团队负责人解释团队 O，再由成员依次说明个人 O 和关键争议。
2. 讨论优先级、承接范围、结果标准、主责与协作者；把建议记录为可执行修改项。
3. 对尚未达成一致的内容，在相关上级或负责人在场时确认最终分工。
4. 控制单场范围；关联人员过多时按业务拆场，每场以能完成有效讨论为准。

### 会后

1. 修改 O/KR，补入共识、指标、日期、协作关系和评论结论。
2. 再次检查上下级承接、同级依赖、术语、敏感信息和主责唯一性。
3. 读回飞书系统状态；把“已修改”“已保存”“已发布”“已对齐”分别报告。

## 对齐检查表

| 检查项 | 通过标准 |
|---|---|
| 顺序 | 承接上级 O 时尽量保持相同优先级顺序；高优目标放前 |
| 主责 | 每个关键结果有一个明确 Owner，协作者不替代主责 |
| 协作 | 主要协作者已知情，必要时在系统中 @；协作者数量保持克制 |
| 依赖 | 写明输入、输出、交付节点和验收关系 |
| 冲突 | 识别资源、优先级、时间和数据口径冲突，并留下决策结论 |
| 范围 | 不把不同工作范围的 KR 混进同一个 O |
| 术语 | 组织内同一概念使用同一名称，不自造近义词 |
| 可见性 | 敏感数据按确认口径脱敏，必要内容单独沟通 |
| 历史承接 | 上周期完成结果进入基线或证据；延续事项必须写出本周期新增阶段结果 |
| @ 关系 | 被 @ 形成协作候选；@ 他人形成依赖线索；双方确认后才写成稳定协作关系 |
| 上级承接 | 个人 O/KR 能指向直属上级当前周期的具体结果或明确协作边界 |

## 飞书系统约束

- 对齐关系挂在 Objective 与 Objective 之间；KR 的协作需要通过内容、@ 和评论表达。
- 系统不允许目标对齐自身；两个目标所属周期需要存在时间重叠。
- “建议对齐”“存在关联”“已创建对齐关系”是三种不同状态，不能混写。
- 系统中的权重和分数属于不同概念；权重表达重要性，分数表达评分，进度表达当前完成程度。

## 冲突处理顺序

先确认共同结果，再确认主责，再确认协作投入和时间节点，最后调整文字、权重和系统关系。无法达成一致时保留争议，不替用户做组织决策。
