# 飞书 OKR 操作与安全边界

本文件只保留草稿助手需要的操作规则；细节以当前 `lark-okr` Skill 和 CLI 帮助为准。

## 资料来源优先级

按任务需要组合来源：

1. 当前周期的本人、上级、团队和协作方 OKR；
2. 最近历史周期的 O/KR、进展、评分、评论和对齐关系；
3. 绩效总结、H1 自评、工作复盘、会议纪要和用户明确输入；
4. 飞书 OKR 制定、撰写、对齐规范与岗位示例。

接口提供结构化字段，页面提供可见的保存、发布、评论和批量粘贴状态；两类证据可以互补。

## 四类关系读取清单

起草个人当前周期 OKR 时，至少形成以下四个独立快照：

| 快照 | 首要读取对象 | 要回答的问题 | 证据不足时的处理 |
|---|---|---|---|
| 上周期完成情况 | 本人上一周期 O/KR、指标、进展、评分、评论 | 哪些结果完成、未完成、变化或缺证据？ | 保留为历史事实或 `[完成度待确认]` |
| 本周期被 @ | 当前周期本人 O/KR 页面中的 @、协作内容和评论 | 谁期待本人提供什么，时间和责任边界是什么？ | 记为候选协作，不自动写入承诺 |
| 上周期 @ 他人 | 本人上一周期 O/KR 中的 @、协作内容和闭环结果 | 哪些协作关系持续有效，哪些已经失效或反复发生？ | 只保留有当前周期依据的关系 |
| 直属上级 OKR | 直属上级当前周期 O/KR，必要时看上一周期 | 个人目标承接哪条上级结果，承接深度和边界是什么？ | 标注“上级 OKR 未核验”，不猜测承接关系 |

接口可读取 O/KR、进展、指标和对齐关系时优先使用接口；@、评论、页面展示顺序和部分协作语义可能仍需页面核验。无法获得某类快照时，输出读取边界，避免用相邻来源替代它。

关系台账字段建议固定为：`关系类型 / 周期 / 来源对象 / O-KR / 对方 / 协作期待 / 当前处理 / 核验状态`。

## 核心实体

```text
Cycle → Objective → Key Result → Indicator / Progress

Objective ↔ Objective = Alignment
```

- Cycle 是用户在一个时间段内的 OKR 容器。
- Objective 是方向、价值和周期内目标。
- Key Result 是判断 Objective 是否实现的结果。
- Indicator 是数字化度量；Progress 是阶段进展记录；Score 是评分。
- Alignment 只连接两个 Objective。

## 只读路径

先读取共享认证规则，再执行用户身份的只读命令：

```bash
lark-cli auth status --json --verify
lark-cli contact +get-user --as user
lark-cli okr +cycle-list --user-id "<open_id>" --as user
lark-cli okr +cycle-detail --cycle-id "<cycle_id>" --as user
lark-cli okr objective.alignments list --objective-id "<objective_id>" --as user
```

按需读取指标和进展；不要为了生成草稿改动进度、分数或备注。

## 草稿与写入

普通文本优先使用 SemiPlainContent：

```json
{"text":"提升核心客户续约质量","mention":["ou_xxx"]}
```

多个 O/KR 可用：

```bash
lark-cli okr +batch-create --cycle-id "<cycle_id>" \
  --input '[{"text":"...","krs":[{"text":"..."}]}]' \
  --dry-run --as user
```

单个 O 或 KR 使用 `+create`。需要复杂链接或富文本时才使用 `richtext` ContentBlock。

### @ 协作者

1. 先用 `lark-cli contact +search-user --query "姓名或邮箱" --as user` 解析身份；命中多个候选时要求用户选择。
2. API 写入时，把已核验的 `open_id` 放入对应 O/KR 的 `mention` 数组；`mention` 会以真实 @ 用户的形式附加到该条内容。
3. 需要控制 @ 在正文中的位置时，使用 `richtext` 的 `paragraph_element_type: "mention"` 与 `user_id`。
4. 页面写入时使用可见的用户选择器；普通文本 `@姓名` 不能当作真实 mention 的成功证据。
5. 写入回读同时核对 mention；正文落地但 mention 缺失时，报告为“已保存，未完成艾特”。

写入前必须确认：

1. 当前身份是目标用户，租户没有混用；
2. 周期 ID、目标归属和完整正文已经核验；
3. 用户明确要求保存或写入；
4. dry-run 请求符合预期；
5. 写入后可以重新读取并核对结果。
6. 每个 mention 的身份、对象和理由已经核验；不能用模糊姓名、猜测的 open_id 或跨租户身份写入。

`--dry-run` 仍可能先检查 OKR 写入 scope；出现权限错误时，不能据此判断请求正文有误。保留本地草稿，待权限具备后重新做 dry-run。

## 页面回退路径

接口无法读取或写入时，使用已登录的飞书 OKR 页面：

1. 从当前用户页面、关注/上级页面或用户提供的目标链接进入；
2. 读取当前周期和历史周期的可见 O/KR，保留页面 URL、周期和读取时间；
3. 新草稿可通过“批量粘贴 OKR”进入解析预览；
4. 解析预览只说明文本被识别，保存后页面出现“已保存”才说明草稿落地；
5. “发布”按钮仍存在，才能确认没有发布；
6. 页面关闭、弹窗消失或控件数量变化后，重新获取页面状态再继续。

浏览器操作遵循只读优先、可见状态优先和最小导航原则；不读取 cookies、存储、密码或隐藏状态，不通过猜测 URL 绕过登录或权限。

## 权限失败

`auth status --verify` 通过只代表身份有效，不代表 OKR scope 已开通。出现 `missing_scope`、`app_scope_not_applied` 或组织安全策略限制时：

- 记录具体 scope 和失败环节；
- 不切换租户、不用 bot 绕过用户权限、不反复重试；
- 在可行时用已授权的飞书文档或用户提供的材料继续做只读草稿；
- 只在用户明确要求并且组织允许时发起增量授权。

## 回读要求

写入成功只代表接口返回成功。必须回读周期详情，核对：

- O/KR 数量与文本；
- 顺序和权重；
- 截止日期和目标周期；
- mention、备注和对齐状态；
- 保存、发布或草稿状态。

任何一项无法核对，都只能报告“请求已返回”或“本地草稿已生成”，不能报告为最终完成。
